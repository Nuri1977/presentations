[Slide 3: The Old Way]
Speaker: Let's take a quick look back. For years, data lakes were just raw Parquet files dumped into S3 directories. It was efficient to scan, but processing them meant writing fragile Java MapReduce jobs. Partitions were hard-coded and concurrent writing often corrupted data.

[Slide 4: 2008 The Hive Era]
Speaker: Hive changed the game in 2008 by bringing a SQL interface to the data lake. You could query with standard SQL. But as data grew, Hive showed its limits. Changing a schema meant rewriting the whole table. And without proper ACID guarantees initially, you were constantly battling delta files and compactions.

[Slide 5: 2017 Enter Apache Iceberg]
Speaker: In 2017, Netflix engineers decided to fix this from the ground up and built Apache Iceberg. Iceberg treats your data lake files like actual database tables. It gives you real ACID transactions, true schema evolution, hidden partitioning, and time travel. The secret sauce? It stores all metadata right alongside the data in the lake.

[Slide 6: Inside Iceberg - The Layers]
Speaker: Let's break down how this works. At the bottom, you have immutable Parquet Data Files. Above that, Manifest Files track these data files. Then, Manifest Lists organize those manifests. Finally, the Metadata File ties it all together. Because everything is immutable, adding data simply means writing new files and a new snapshot.

[Slide 7: Architecture - The Catalog]
Speaker: To find these metadata files, Iceberg uses a Catalog. The Catalog maps a table name to the current metadata file in storage. It acts as the atomic pointer swap that makes safe concurrent writes possible. This open standard allows for various implementations, which we'll see shortly.
