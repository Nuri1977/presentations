🏔️ Apache Iceberg · Background

The old way was painful

For years, data lakes were raw Parquet files dumped into S3 directories — fast to scan, painful to manage.

  • 📁Hard-coded partition paths — wrong at creation time, stuck forever
  • 💀200-line Java MapReduce to read what SQL does in one line
  • ⚡No transactions — concurrent writes silently corrupted data
  • 🔀Schema changes broke pipelines — rename = full table rewrite
It worked, kind of. But fragile, error-prone — you could never guarantee correctness.

THE OLD WAY

# Hadoop MapReduce (Java) circa 2010 public class SalesAggregator { void map(Text key, Text val) { // parse s3://bucket/year=2024/... // hope nobody else is writing // pray schema didn't change } }
✕ Result: Corrupted data, broken pipelines, sleepless nights
📅 2008 · The Hive Era

Hive changed the game — then hit its limits

✅ WHAT HIVE BROUGHT

  • ✓SQL interface — SELECT * FROM sales
  • ✓Table schemas and partitions
  • ✓Centralized Metastore

✕ BUT THE PROBLEMS

  • !Schema evolution — rename/drop = full table rewrite
  • !Partitions hard-coded — wrong choice, stuck forever
  • !No ACID until 2014 — ORC only, constant compaction needed

Real-world pain points

Concurrent writes → silent data corruption
ACID (2014) → delta files requiring constant compaction
Metadata outside the lake → syncing nightmares across engines
Other engines (Spark, Trino) → never seamless
🚀 2017 · Enter Apache Iceberg

Netflix started over. They built it right.

Engineers at Netflix designed an open table format that treats data lake files like actual database tables — with all the guarantees of a transactional database.

⚡

Real ACID

True transactions with safe concurrent writes

🔄

Schema Evolution

Add, rename, drop columns safely

⏪

Time Travel

Query any historical snapshot like Git commits

🗂️

Hidden Partitioning

Partition scheme evolves as queries change

THE ICEBERG WAY

-- Just SQL. No Java. No tears. SELECT * FROM iceberg.sales LIMIT 100; -- Time travel: query yesterday SELECT * FROM iceberg.sales FOR VERSION AS OF 43782831; -- Safe rename, no rewrite ALTER TABLE iceberg.sales RENAME COLUMN rev TO revenue;
✅ Metadata lives in the lake. Everything is immutable. Time travel is free.
🏗️ Architecture · The Iceberg Layers

Inside Iceberg: a metadata tree

📄 Metadata File
Schema · Partitioning · Snapshot history — the single source of truth. Like a Git repo root.
↕
📋 Manifest Lists
Lists of manifests with rolled-up stats. Enables skipping entire partitions without opening files.
↕
📑 Manifest Files
Tracks data files + stats (row count, min/max). Query engines skip files without scanning.
↕
🗄️ Data Files
Immutable Parquet/ORC/Avro. New data = new files at every level.

🔑 The Key Insight: Everything is Immutable

  • 📸A Snapshot = frozen table state — like a Git commit
  • ➕Adding data = new files at every level — old files untouched
  • ⏪Old snapshots remain → time travel is free
  • 🛡️Immutability enables ACID, schema evolution, concurrent writes
Snapshot S0 → Manifest List → Manifests → Data Files
Snapshot S1 → New Manifest List → Old + New Manifests → All Files
🗺️ Architecture · The Catalog

The Catalog: the missing glue

How does a query engine find a table's metadata file? You can't hard-code an S3 path — it changes with every snapshot.

The Catalog does 3 things:

  • 🗺️Maps table names → metadata file location in object storage
  • ⚛️Atomic pointer swap — one atomic operation. Safe concurrent writes.
  • 🤝Coordinates, never writes — your engine writes files. Catalog tracks current version.
The Iceberg REST Catalog spec is an open standard — Polaris, Lakekeeper, Nessie all implement it.

⏪ Time Travel · Snapshot History

Time travel: every commit, forever

The History tab shows every snapshot committed to this table — your Git log for data.

  • 📸Snapshot ID — unique 64-bit identifier, like a Git hash
  • 🔧Operation — append, overwrite, delete
  • 📅Committed At — exact timestamp of each write
  • ➕Added Records / Total Records — per-snapshot row counts

Query a specific snapshot:

SELECT * FROM iceberg.test_namespace.titanic FOR VERSION AS OF 2652326968643782831;

🤖 SQL Editor · AI-Powered Import

Import CSV/Parquet with AI assistance

The AI Agent (Gemini) generates the correct DuckDB CTAS statement to import a local CSV file as a new Iceberg table.

  • 📁+ Import Data — pick Local File (CSV, Parquet, JSON)
  • 🤖AI generates schema-inferred CTAS statement automatically
  • ✅Allow / Deny — review and approve before execution
  • 🔍Verify immediately — agent runs a SELECT to confirm row count
