Chapter 07

Pipeline modules

A pipeline step selects a versioned plugin ID and supplies the fields required by that plugin contract. DBT Studio authors and validates these declarations; the selected execution runtime performs them.

6 addable modules1 preserve-only module@v1 contracts
Terminology: the UI presents these as palette modules or step types, while the YAML field is named plugin. For example, the dbt module is persisted as plugin: dbt@v1.

Modules visible in the palette

dbt · dbt@v1

Runs dbt operations such as build, test, compile, debug, seed, or dependencies. The command is required; working directory is optional.

- name: Build models
  plugin: dbt@v1
  command: dbt run
  working_dir: dbt

Default command: dbt run

Rosetta · rosetta@v1

Runs a Rosetta CLI command. It is used for Rosetta-native data engineering work rather than dbt commands.

- name: Apply layer
  plugin: rosetta@v1
  command: rosetta apply -s bigquery
  working_dir: rosetta

Required: command. Optional: working directory.

🟪 Terraform · terraform@v1

Runs Terraform CLI commands for infrastructure work. Its optional working directory should contain the relevant .tf configuration.

- name: Provision
  plugin: terraform@v1
  command: terraform init && terraform apply -auto-approve
  working_dir: terraform

The displayed default initializes and applies with auto-approval.

⬛ Shell · command@v1

Runs a general command when a specialized module is not appropriate. Only the command field belongs to the current editor contract.

- name: Announce
  plugin: command@v1
  command: echo "pipeline started"

Because this is generic execution, authors must review command content carefully.

🟡 S3 · s3@v1

Represents an Amazon S3 command step, commonly used to copy or synchronize pipeline artifacts.

- name: Upload results
  plugin: s3@v1
  command: aws s3 cp results/ s3://my-bucket/ --recursive

The current editor contract requires a command and does not expose a working-directory field.

Kinetica CLI · kinetica_cli@v1

Runs KiSQL commands against Kinetica. Local Runner settings manage the KiSQL CLI dependency used by this kind of step.

- name: Check Kinetica
  plugin: kinetica_cli@v1
  command: kisql --url http://localhost:9191 --sql "SELECT 1"

The command is required. Connection values should come from the intended environment rather than documentation examples.

Compatibility-only module

Git clone · git_clone@v1

The shared contract and serializer understand URL, optional branch, and optional destination fields. However, this module is marked preserve-only: it is not shown in the current palette, and Project Agent generate/update must not introduce it.

- name: Fetch dependency
  plugin: git_clone@v1
  url: https://example.com/repository.git
  branch: main
  dest: dependencies/example

How definitions are split

Shared catalog

PIPELINE_PLUGIN_CATALOG is serializable and contains IDs, availability, fields, labels, placeholders, and defaults. Backend Project Agent validation consumes this contract.

Renderer definitions

PLUGIN_DEFS adds MUI icons, colors, categories, and fields for the visual palette. It contains only the six addable modules.

Important implementation boundary: DBT Studio's catalog describes how a step is authored and validated. It does not itself implement dbt, Terraform, AWS, KiSQL, or Rosetta command semantics. Local Runner or Rosetta Cloud executes the saved plugin contract and must have the required tools, configuration, and credentials.

Project Agent behavior

The Agent is instructed to use dbt@v1 for dbt operations—not invented IDs such as dbt-run. Unknown plugins and git_clone@v1 can be preserved when already present but cannot be introduced. For Terraform steps, it inspects the working directory for suitable .tf files before finalizing the pipeline.
